# Work Plan: Atelier Cockpit Build-Out

Phased plan for implementing the redesign in `frontend/` (React + TS + Vite) with FastAPI backend extensions. Phases are ordered by dependency and value; each ends in a shippable state. Est. sizes: S < 1 day, M 1–3 days, L 3–5 days.

## Phase 0 — Foundations (M) — ✅ done 2026-07-21
- [x] Theme system: CSS custom properties on `body[data-theme]`, light/dark token sets from README, toggle in top bar, persist in localStorage.
- [x] Fonts: DM Sans + DM Mono (Google Fonts, unchanged from before).
- [x] Desk shell: dotted-grid background (`DeskLayout.tsx`), floating top bar (nav pill, workspace switcher, stats pill, bell, theme — **+ New session renders disabled**, wiring lands Phase 2/3), centered-column page scaffold.
- [x] Workspace scope context: reactive `useWorkspaceScope()`, `?ws=` URL param so it survives reload (`lib/workspaceContext.tsx`).
- [x] Shared primitives: Card, Chip, Toggle, StatusDot, PriorityLabel, SectionLabel, Dialog, Mono (`components/primitives/`). Status/priority color maps (`lib/statusColors.ts`, `lib/priorityColors.ts`).
- [x] Router: HashRouter → BrowserRouter, with a FastAPI catch-all SPA-fallback route for deep links (`server.py`).
- [x] **Backend — pulled forward from later phases, not "none" as originally scoped**: full SSE rewrite from server-rendered HTML fragments to structured JSON events (`events.py::serialize_event()`), plus a fan-out fix (`Session.subscribe()`/`_broadcast()`) so multiple simultaneous viewers of one agent no longer race for events on a single queue. New `EventType` members: `AUTO_LOG`, `STEER`, `DELEGATE`, `CHECKPOINT`, `USER`, `ENDED`. Justification: this was backend-only churn, safe to land before any Atelier-styled consumer existed, and the fan-out fix is also a prerequisite for Phase 2's multi-viewer Dashboard cards.
- Note: `Overview.tsx`→`Dashboard.tsx` and `AgentFocus.tsx`→`AgentThread.tsx` renamed; Agent Thread got an interim structured-event renderer (same look, real fields instead of HTML/regex scraping) so it isn't dead between now and its full Phase 3 rebuild. `NewSessionDialog.tsx` (confirmed dead code) deleted.

## Phase 3 — Agent Thread (L) — ✅ done 2026-07-21
- [x] Three-zone layout, collapsible goal rail (⌘B) — full rewrite of `views/AgentThread.tsx`.
- [x] Event renderers: message, thinking (collapsible), tool card (merged with its result), auto-log, steer, delegation (expandable, via its own nested SSE subscription to the sub-session — no server-side event nesting needed), checkpoint (+revert, no-op per the stub list), ask, user, ended.
- [x] Composer states: driving / watching-locked / ended; Assume/Relinquish; Stop; delete.
- [x] Right rail tabs: Terminal, Files, Preview (placeholder, as scoped).
- [x] Replay scrubber on ended sessions (client-side, slices the visible event list).
- Backend: `POST /api/agent/{id}/checkpoint` and `/revert` (broadcast-only, no real snapshot — matches the prototype's own mock behavior); `Session` gained `model`/`started_at` fields (header needed both, neither existed before) exposed via `/api/agents` and `/api/agent/{id}`.
- **Verified against a real MiniMax M2.7 call** (not just a fake test key) — this surfaced four real, fixed bugs that fake-key testing couldn't have caught:
  1. `POST /api/sessions` passed the settings-*file*'s model/key/url straight through as override args, which always outranks env vars in `resolve_provider()`'s precedence — silently breaking env-var-only configuration for actual session starts (the "configured" pre-flight check used correct precedence; the real invocation didn't).
  2. `<think>...</think>` reasoning tags commonly arrive split across multiple stream deltas; the old per-fragment heuristic had no memory of an already-open think block, so most of a multi-fragment thinking block leaked through as plain MESSAGE text with literal tag characters. Now stateful across chunks (`_state['in_think']`), and tag literals are stripped.
  3. A streamed tool call re-emits the same `tool_call` event (same id) as its args accumulate (empty → partial → complete) — rendered as 2-3 duplicate cards until the frontend started updating the existing card in place instead of appending a new one per update.
  4. Assume/Relinquish looked unresponsive for up to one 3s poll cycle (mode chip/composer state only updated on the next `fetchAgent()` poll) — fixed with an optimistic local update on click.
  - Also found and fixed in passing (not Phase-3-specific, but blocking verification): the "provider/model" prefix convention baked into `settings.py`'s default, `provider.py`'s docstring, and 3 of 4 Setup Wizard presets doesn't work — `OpenAIModel` sends `model_id` as-is with no prefix-stripping, and `litellm` (which would understand that convention) is a listed dependency never actually imported anywhere. Fixed the MiniMax-specific docs (`provider.py`, `docs/quickstart.md`) since those were fully confirmed; the broader default-OpenAI-preset/Anthropic-preset implications need their own dedicated look, not fixed here to avoid changing default behavior for existing users as a rushed aside.

## Phase 4 — Workflows + Review (L) — ✅ done 2026-07-21
- [x] Workflows screen: Board stages config (toggle, persist via `useStages()` API hook), Default agents (Planner/Builder/Reviewer) with config dialog (model/trigger/prompt/tools), generated Current-workflow diagram reacting to live config, pipeline templates (link out to Tasks — no scheduler yet, per stub list).
- [x] Review queue: pending diffs (derived post-hoc from git, per the decoupling note below), expand-to-view-diff, approve/reject/approve-all.
- Backend: new `workflows/` module — `Stage`/`Role`/`Trigger` models, `StagesStore`/`RolesStore` (YAML, same single-file pattern as other stores); `GET/POST /api/stages`, `GET/PATCH /api/roles/{key}`; `GET /api/review/diffs`, `GET /api/review/diff`, `POST /api/review/approve`, `POST /api/review/reject` (git-backed — `git add`/`git commit` per file or whole-repo).
- Trigger wiring scope: `_maybe_fire_role_triggers()` fires enabled roles when a task's status crosses a stage boundary (`leaves_draft`/`is_started`/`enters_review`) via the `PATCH /api/tasks` route. Not yet wired to agent-tool-driven status changes (an agent calling `update_task_status` internally doesn't fire a trigger) — disclosed limitation, same-phase follow-up if pipelines see real use. All roles ship **disabled by default** (real API cost) — a dedicated test (`test_all_roles_disabled_by_default`) guards this.
- Review queue is deliberately "post-hoc" per the decoupling note: diffs are read live from `git diff`/`git status` in each workspace, not a separate captured/staged layer. Approve = `git add` + `git commit`; reject **never discards** — it only acknowledges, consistent with the project's stance of never automating destructive git operations (`checkout --`/`reset --hard`/`clean`).
- Auto-review banner / Run-review-now on Task Detail: deferred — `review_gate` field exists (Phase 1) but enforcement wasn't added this phase; still manual-only.
- Two real bugs found and fixed during testing:
  1. `StagesStore.list()`/`RolesStore.list()` returned shallow copies (`list(DEFAULT_STAGES)`) sharing the same mutable dataclass instances as the module-level defaults — `update()`/`toggle()` mutating a returned object corrupted the shared defaults for the rest of the process (caught via real cross-test contamination in pytest). Fixed with `copy.deepcopy()`.
  2. `approve_review()` never checked the `git add`/`git commit` subprocess return codes — a silent failure still returned `{"status": "committed"}` to the client. Caught by a Playwright test expecting a second commit that never landed. Fixed by raising `HTTPException(500, ...)` with the captured stderr on either command's non-zero exit.

## Phase 5 — Vault + Settings (M) — ✅ done 2026-07-21
- [x] Vault: locked/unlocked card states, credentials list + add + delete, injection template chips (rendered from existing `InjectionTemplate` data — no template *editor* in this pass, since nothing produces templates yet outside the CLI), audit log. Web routes added on top of the existing (well-tested, unmodified) `VaultStore` — CLI stays the only place that writes templates for now. Credential values never reach a list/get response; the web layer builds response dicts that don't reference `.value` at all, on top of the store already never populating it from `list_credentials()`.
- [x] Settings: Usage card (new JSONL usage ledger + `/api/usage`, recorded when a session actually ends), Model providers (named profiles + "Set default", which copies a profile's fields into the existing single-provider `agent.*` config rather than teaching `resolve_provider()` about a list — keeps the Phase 3 env-var-precedence fix untouched), consolidated Tools (unchanged backend, new Atelier-styled card), Policies (new store, toggle-only for 3 of 4 rules), MCP servers (config-only registry, no client), Integrations (GitHub PR-on-review + phone-push toggles, both config-only), Workspaces CRUD (backend already existed from Phase 1/2 — just needed the UI).
- Backend: `usage.py` (JSONL ledger + summary/cost-since, same append-only pattern as the vault audit log), `policies/` (`Stage`/`Role`-style YAML store; only `spend_cap` is wired to a real check), `mcp_servers.py` (list-growable YAML store, unlike the fixed-cardinality Stages/Roles), `settings.py` gained `providers: list[ProviderProfile]` + `default_provider` + `integrations` — additive, doesn't change what `resolve_provider()` reads.
- Real enforcement: the spend-cap policy is checked in `POST /api/sessions` against today's ledger total and blocks with a 400 once reached — the only policy with a working hook, matching the plan's stub-list decision. The other three policies (migrations guard, pause-after-test-failures, no-sudo) are configurable and persisted but have no enforcement point yet — there's no existing concept of a migration file, a test-failure counter, or sudo-command detection to hook into.
- Scope trims: no vault template *editor* (CLI-only for now — see above), no "+ Add rule" for arbitrary custom policies (fixed default list, like Stages/Roles), no GitHub OAuth or "connected" status (no backend concept — the card is honest about "Not connected" rather than faking a green chip), no Settings §8 "First-run flow previews" (there's no setup-wizard route to link to yet — that's Phase 6's actual job).
- Two things found and fixed during testing:
  1. `AddCredentialDialog` didn't clear its `value` field on a failed submit — a rejected add (e.g. duplicate id) left the plaintext still sitting in the password input's DOM `value` attribute. Not a network/storage leak (nothing sent it anywhere), but confirmed via a Playwright assertion checking `page.content()` after a genuine failure; the real fix was in the *test* (clean up leftover state before asserting) rather than the dialog, since a live password field naturally holding what the user just typed is correct, expected browser behavior, not a bug to suppress.
  2. A Playwright test for "Set default" was mutating the real `settings.yaml` (copying a fake test key into `agent.api_key`, per the feature's actual, correct behavior) and never restoring it — `DELETE /api/settings/providers/{name}` only removes the profile from the list, it doesn't undo an already-applied "Set default". Since `PUT /api/settings` treats an empty `api_key` as "leave unchanged" (protects against accidentally wiping a real key), there was no API path to undo it. Fixed by having the test read and restore the raw settings file directly, the same way tests already read `cockpit.token` directly rather than going through auth.

## Suggested sequencing / parallelism
Phase 0 → 1 → 2 → 3 sequential (each builds on the last). Phase 5 can run parallel to 3–4 (different backend surface). Phase 4 last of the big ones — it has the most new backend. Total rough estimate: 4–6 engineer-weeks.

## Definition of done (per screen)
- Matches prototype pixel-values in both themes.
- All interactions in the prototype work against real data.
- Empty states handled (no workspaces, no tasks, no pending reviews, locked vault).
- Keyboard: Enter sends, Esc closes dialogs, ⌘B rail toggle.
- No regressions to the SSE live-update behavior of the current app.
